# Changelog

## 0.1.0 (unreleased)

The first review plugin, beside `birdiz-audit` in the `birdiz` marketplace
and installable without it: `/plugin install birdiz-review@birdiz`. It
carries its own copy of the finding core
([ADR 0005](../../docs/adr/0005-two-plugins-share-a-copied-core.md)).

This release is the bare review run, end to end
([#38](https://github.com/Birdiz/skills/issues/38)). No content detector
and no judgment step exists yet, so every changed file is `unproven` and
the brief says which dimensions did not run.

- `review-pr` takes a branch, compared with the remote's default branch, or
  a `base..head` range, and refuses an empty diff or an unknown ref without
  writing anything.
- Each run writes a directory under
  `$XDG_STATE_HOME/birdiz-review/runs/<repo>/<branch>/<head short sha>/`
  (`~/.local/state` by default), never inside the reviewed repository:
  nothing is checked out, trees are read from git objects, the working copy
  is never read or written
  ([ADR 0006](../../docs/adr/0006-review-invariants.md)).
- The run header records the detector tools looked for on this machine,
  found or not, with the version of each one found.
- The git file-change signals: every changed file, renames detected, the
  new directories, a signal on each file added, deleted, renamed, copied or
  changed in type.
- The brief, a projection of the run header, the detector outputs and the
  findings files, regenerated by `brief.py`: declared against detected
  risk, a bucket for every changed file (`must-read`, `glance`, `skim`,
  `unproven`) by fixed rules, the coverage gaps with the dimensions not run,
  and a proposed verdict (`merge`, `fix`, `close-and-reprompt`) with its
  round, the number of distinct heads reviewed on the branch.
- The review validator, `validate.py`: the finding core with the review
  extension (axes `INT`, `BRK`, `STR`; keys `diff`, `attention`,
  `blocks_merge`, `fan_in`, `declared` and `detected`; the prose section
  **Reviewer question.**), plus the run header, the detector outputs, one
  bucket per changed file, skim proofs that rest on content detectors, and
  the verdict line. `--require brief` fails on a brief that is not the
  projection of the files as they are. `check-pointers.py` opens the
  findings' pointers in the head tree.

The repo facts and the risk map
([#39](https://github.com/Birdiz/skills/issues/39)):

- `review-setup`, run once per repository. `detect.py` writes nothing and
  reports the stacks, the detector tools this machine has (never stored),
  the Pocock artifacts with their shape (`ok`, `missing`, `drift`,
  `unchecked` for a freeform tracker, `absent` for a glossary or ADR
  directory not created yet), and risk zones proposed each with a pointer
  to what suggested it. `write.py` writes only what the user confirmed:
  `docs/agents/review.md` (stacks and the risk map, nothing else) and a
  `### Review` subsection inside the `## Agent skills` block, leaving the
  other subsections as they are. It refuses on a detached HEAD, on the head
  of an open PR (checked with `gh` when present), or on a branch
  `review-pr` has a run for.
- Risk map globs are gitignore-like: `*` within a directory, `**` across
  them, a glob without `/` matches a name at any depth.
- `review-pr` reads the risk map committed at the base, records it in the
  run header (`risk_map`), and names the zone of every changed file in it.
  Such a file lands in `must-read`, `unproven` or `glance`, never `skim`,
  and the validator rejects a brief that puts one there. The brief's
  coverage gaps say whether the risk map was found and which rows were
  left out.

The spec, the tickets and the Pocock contract
([#40](https://github.com/Birdiz/skills/issues/40)):

- `review-pr --pr <number>` reviews a pull request. It reads the PR with
  `gh`, and fetches its head (and base) from origin by ref when the
  repository lacks them: objects only, no ref written, nothing checked out.
  Its run directory is keyed by the PR's head branch, so its rounds add up
  with branch runs.
- Every run looks for what the change was supposed to do, first match
  wins. The order: the user's answer (`--spec #N | <path>`, `--no-spec`);
  the closing references in the PR body; issue references in the commits;
  a spec file under `docs/`, `specs/` or `.scratch/` named after the
  branch. When nothing is found, an `ASK:` line tells the skill to ask the
  user.
- Issues are read through the tracker the tracker doc names at the base:
  GitHub with `gh`, local markdown from the head tree. Other trackers, and
  a missing tracker doc, make intent `not-evaluable` with the reason. A
  ticket's parent is its spec. A spec's tickets are its sub-issues, else
  the issues with a `Part of #<spec>` line, else the `issues/` files
  beside a local spec. The tickets the PR closes are in scope, and the
  others are siblings.
- Each artifact is checked against the Pocock contract when it is read.
  Acceptance criteria are read in both `to-tickets` templates. A GitHub
  ticket without `Parent` or `Blocked by` sections is not drift. A PR body
  without `Merge Danger` is "not declared". A missing section the review
  relies on is contract drift, and makes the dimension it feeds
  `not-evaluable (contract drift: <artifact>, <what>)`. The run continues.
- The run writes `sources.json` and a copy of each artifact under
  `sources/`. The brief states the PR's declared Door and Blast Radius, or
  that the risk was not declared, and lists the spec and tickets found and
  any drift among its coverage gaps. The validator checks `sources.json`.
- [`pocock-contract.md`](skills/review-pr/pocock-contract.md) lists each
  artifact read, the sections relied on and the upstream commit last
  checked (`mattpocock/skills@abeeaf9`).
  [ADR 0007](../../docs/adr/0007-pocock-artifact-contract.md) records the
  decision. `review-setup` checks the tracker doc with the same code.

The intent step ([#41](https://github.com/Birdiz/skills/issues/41)):

- The first judgment step, [`steps/intent.md`](skills/review-pr/steps/intent.md),
  a reference file of `review-pr`. It reads files in the run directory and
  writes `findings/intent.md` only, with no question. `review-pr` runs it
  in a sub-agent with fresh context when there is one, in order otherwise.
- Each run writes `diff.patch`, the diff the judgment steps read, and the
  `hunks` of each changed file (new-side line ranges) in the git changes.
- When the intent sources are evaluable, `run.py` writes the intent
  worksheet (one row per acceptance criterion of the in-scope tickets, one
  row per changed file, `?` where the step judges) and prints a
  `STEP: intent <step file>` line. The step maps each criterion to the
  hunks that implement it (`found`, `partial`, `not found`), justifies each
  changed file by a criterion, a ticket or the spec, or flags it `out of
  scope`, and flags each change against the spec's Implementation
  Decisions or Out of Scope. Each `partial` or `not found` criterion, file
  out of scope and decision broken is an `INT` finding, and every `INT`
  finding is cited by a row.
- The validator checks the tables against `sources.json`, the changed files
  and their hunks: every criterion and every file has one row, hunks meet a
  change, a sibling ticket never justifies a file, a decision row points
  into the spec's Implementation Decisions or Out of Scope. A worksheet the
  step has not filled is `PENDING intent`, an error with
  `--require intent`.
- The verdict proposes `close-and-reprompt` for misread intent: more than
  half of the criteria not found, a file out of scope, or a change against
  a stated decision. A reason line counts the tables. When intent can't be
  evaluated (no spec, contract drift), the verdict starts with "intent not
  checked: <why>" and misread intent is not offered. The stop rule (a third
  distinct head with a `blocks_merge` finding) is unchanged.
- The brief lists the `must-read` and `glance` findings that point at no
  changed file, such as a criterion not found, after the files of their
  section.
